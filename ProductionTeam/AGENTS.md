# ProductionTeam

「AI×エンタメで人を楽しませながら収益化する」というチャンネル目標から逆算し、企画、台本、画像、音声、編集、検証、投稿準備までを一貫して設計する制作チーム。

チャンネルの長期方針は `../CHANNEL_VISION.md` を正とし、現在はPhase 1「Shortsで認知と勝ち筋を探索」を最優先する。採用中の企画形式に対応する制作スキルと仕様を使用する。

大喜利制作では `skills/write-visual-ogiri-scripts/SKILL.md` を読み、担当作業に対応する参照資料を読む。別形式では、その形式に対応するスキルと制作仕様を使用する。

## 起動方法

制作依頼は必ず `production-manager.md` から開始する。制作統括はPlanningTeamの企画意図、OperationTeamの実績、公開予定、既存作品との差を確認し、今回の成功条件を定義する。

ユーザーから題材が指定されていない場合は、制作統括と秘書エージェントが構成作家にお題候補を作らせ、需要、チャンネル適合性、画像化、学習価値まで評価した3案を提案する。承認前に `story.json` を変更しない。

ユーザーがお題を指定した場合は、お題提案を省略して14枚の設計へ進む。

## 担当

- `production-manager.md`: 制作統括、企画意図とKPIの接続、工程判断、完成動画と投稿品質の最終承認
- `secretary-agent.md`: 制作進行、ユーザーへの提案、採否決定、`story.json` の唯一の編集者
- `structure-writer-agent.md`: お題発案、14枚の全体構成、感情曲線、伏線と回収
- `boke-agent.md`: 画像から笑えるボケ候補の量産
- `tsukkomi-agent.md`: ボケの明瞭化、フリップ文と読み上げ文の研磨
- `rhythm-agent.md`: 並び、語感、改行、尺、間、タイトルコール、SEの調整

## 全体判断の入力

制作開始前に、利用可能な範囲で次を確認する。

- OperationTeam: 公開後24時間・7日後の実績、維持率、反応率、伸びた題材と弱点
- PlanningTeam: 市場、季節性、視聴者仮説、今回検証する変数
- 公開カレンダー: 投稿間隔、季節期限、既存予約との題材重複
- 過去作品: 冒頭、尺、14枚の画角、笑いの機構、終わり方の重複
- チャンネル目標: 短期再生だけでなく、独自性、シリーズ認知、収益化可能な継続性

データが少ない場合は勝ち筋を断定せず、今回の作品を比較可能な実験として設計する。

## 制作フロー

1. 制作統括が企画書、運用実績、公開予定を確認し、狙い・視聴者・成功指標・変えない要素を定義する。
2. 構成作家がお題候補を5案作り、需要、独自性、14枚の視覚差、検証価値を採点する。
3. 秘書が上位3案を、狙い・画像の広がり・前回との差・公開適期とともにユーザーへ提案する。
4. お題決定後、構成作家が14枠の役割と画の方向を設計する。
5. ボケが各枠に複数候補を作る。
6. ツッコミが意味と笑いを明確にし、表示文と読みを整える。
7. リズム感が14本を並べ替え、間・尺・SE・タイトル位置を決める。
8. 秘書が全14本を監査し、`story.json` に反映してJSONとプロジェクト仕様を検証する。
9. 制作統括が画像、上側フリップ安全域、音声、BGM、効果、冒頭離脱対策、終盤の回収を横断監査する。
10. レンダリング後、代表フレーム、映像・音声仕様、尺、破損、投稿メタデータとの一致を確認する。
11. OperationTeamへ、今回の仮説、変更点、公開後の判定指標を引き渡す。

## 画像先行の必須契約

全回答は次の情報を揃える。不足した案は秘書が差し戻す。

```text
id: a01-a14
block: 起／承／転／結など
mechanism: あるある／ギャップ／裏切り／自虐／天丼／伏線回収など
flip_text: 画を見た後に出す短いフリップ文
reading: 読み上げ用の自然な文
image_subject: 画面の主役
image_scene: 場所、人物、動作、状況
visual_wrongness: 一目で分かる異常点を1つ
composition: 寄り／引き／俯瞰、主役の位置、背景要素
glance_test: 無音・字幕なしで約1秒見ても状況が分かる理由
image_prompt: 縦長画像を生成できる具体的な指示
duration: 想定尺
se: 効果音
visual_pre_roll: 画像先行ボケの場合のみ0.55-0.75秒
```

## 14枚の視覚品質基準

- 14枚すべてで主役、場所、動作のうち最低1つを変える。
- 同じカウンター越し、同じ人物配置、同じ画角を3枚以上続けない。
- 接写、室内の引き、人物リアクション、物体ボケ、看板・UI、巨大スケールを混ぜる。
- 文字を読まないと成立しない画像は禁止する。
- 異常点を盛り込みすぎず、1枚につき主ボケを1つに絞る。
- 画像上部30-35%を落ち着いたフリップ安全域とし、主役は中央35-75%へ置く。
- Shorts UIと上側フリップの双方を考慮し、画面下部20%にも重要な顔や文字を置かない。
- a14は他の13枚よりスケール、意外性、回収のいずれかを強くする。

## 完了条件

- PlanningTeamの狙いとOperationTeamで測る成功指標が明記されている。
- お題と14回答に重複感がない。
- 全回答に具体的な画像案がある。
- あるある、視覚的な飛躍、リズム区間、回収またはピークが含まれる。
- `text`、`reading`、`duration`、`se`、必要な追加フィールドが整合する。
- `story.json` が有効なJSONで、回答IDと参照IDが一致する。
- 画像、音声、BGM、効果、フリップ、動画尺が同じ台本状態に同期している。
- 完成MP4が縦1080×1920で正常再生でき、代表フレームで主役とフリップが衝突しない。
- タイトルと概要欄が実際の内容、シリーズ方針、公開時期と一致している。

## Codex / Claude Code ハイブリッド制作

素材、台本、ナレーション、BGM、挿し絵、Remotion実装まで完成した後は、`handoffs/README.md` の共通レンダー契約を使う。制作担当は作品ごとに `handoffs/*.render.json` を作り、`status` を `ready` にして引き渡す。

CodexとClaude Codeのどちらが実行しても、次の一つのコマンドだけを使用する。

```powershell
npm run finalize:handoff -- ProductionTeam/handoffs/<episode>.render.json
```

レンダー担当は物語、字幕、タイミング、画像選定を独断で変更しない。契約不備やTypeScriptエラーがあれば制作担当へ戻し、機械QC合格後も代表フレームと音声を人が確認する。YouTube投稿はこの契約に含めず、ユーザーの明示的な投稿依頼を必要とする。
